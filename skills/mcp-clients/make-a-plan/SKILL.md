# Make a plan

Create a plan people can act on: a clear outcome, the next action, a realistic
sequence of work, and the details needed to do it. Keep the overview concise and
connect it to the actual tasks, drafts, bookings, or applications.

Use this for planning and maintaining multi-step work. Answer a quick list or
single-post request directly. Comparing destinations or options is research;
turning an engineering spec into tasks is implementation planning. When an
installed specialist skill better fits the requested outcome, use it without
creating a second plan or tracker.

## Start with what is known

Use the conversation, supplied notes, and named sources first. Identify the goal,
what is already done, hard deadlines versus targets, participants, resources, and
unresolved decisions. Search the relevant Notion area and connected sources for
an existing plan and missing information that changes the work. Keep discovery
bounded to this goal and respect source restrictions.

Read [planning by use case](reference/planning-by-use-case.md) for the relevant
section. Ask only for information needed to avoid building the wrong plan; skip
questions already answered. A missing owner or date need not block a useful first
version. Leave those properties empty and make consequential unknowns visible.
Distinguish source facts from proposed tasks, copy, estimates, and dates.

If the user asks for a preview, show it in chat. If they ask to create the plan,
build within that scope without separate outline and row-approval checkpoints.
Deliver the initial plan before asking optional questions to tune it.

## Put the plan where it belongs

Use a named destination. Otherwise, find and reuse a matching plan and suitable
collections before creating new ones; inspect their schemas and relevant records.
A plan belonging to an established Projects database should be a record there,
with a project-filtered view of its shared Tasks database. A one-off personal plan
can be a private home with a child tracker. Follow the connection's default private
creation mode when no destination is established. Do not ask the user to design a
database or create a portfolio just because this is their first plan.

Keep stable destinations in the sidebar: the plan home, its working tracker, and
any substantial resources. Record pages belong in their databases. Use native
relations for plan membership and dependencies, with linked views filtered to the
specific plan. Reuse existing records on later runs, preserving completion,
comments, source links, and unrelated work. Do not move or replace existing
collections to impose a new layout. Ask about placement later when it would help
integrate a newly created private plan into the team's existing system.

## Work backward from the outcome

Name a few milestones as checkable outcomes, such as “venue confirmed” or
“application ready.” Work backward from a known deadline; account for dependencies,
review, and buffer. If the date is infeasible, show the conflict and a proposed
change rather than silently compressing the work. Never turn a proposed schedule
into an agreed commitment.

For each step, identify what completion requires: a decision, person, budget,
material, booking, or deliverable. Use tools and resources the user already has.
Identify the most consequential risk and a practical alternative. Include only
workstreams that apply to this request.

Use a checklist for a short, one-off sequence. Use a native database when items
need ongoing status, dates, ownership, repeated entry, or distinct working pages;
around five items is a useful signal, not a quota. Choose names and properties
that fit the work: applications and bookings need different states from tasks.

## Build the working pages

Read [page layout and navigation](reference/page-layout.md) before composing the
home. Populate the plan and its records from the available information. A task
body should explain the next step and completion criteria; a deliverable should
contain the requested draft, script, run sheet, packing list, or preparation notes.
Do the requested writing now instead of leaving instructions to write it later.
Label new creative work as draft and keep its review questions nearby.

Store results on the relevant record and link back to the plan. Use a separate
collection only for a distinct kind of work, such as guests alongside event tasks.
Keep private contact details separate from material intended for a wider audience;
a filtered database view does not restrict access to its records.

Use current Notion tool schemas and formatting documentation. Create relation
targets before connecting records, and properties before configuring views. Resolve
people to actual accounts before assigning them. Never invent identities, bookings,
prices, approvals, application submissions, or completed work. A calendar view is
not a scheduled invitation, and a planned publication date is not a scheduled send.
Creating a plan does not authorize purchases, outreach, publishing, or sharing.

## Check and deliver

Read back the saved pages and relevant records. Check milestone order, source
facts, record coverage, native relations, and filters. Keep undated, unassigned,
and blocked work discoverable. After an uncertain write, inspect what exists
before retrying so a resumed run does not duplicate the plan.

Inspect the rendered home and representative detail pages when visual inspection
is available. Check the first action, readable dates and titles, visible properties,
color hierarchy, and routes from home to record and back. Test a narrow reading
width as well as the desktop composition. Report what was actually verified;
never describe a static table as a working database or claim an unsaved plan exists.

Return the home link, what is ready, and one concrete next action. Ask a focused
follow-up only where it improves this plan, such as confirming the decision maker
or choosing a target date. Continue on the same records when the user answers.
