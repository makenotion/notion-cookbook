# Semester study-desk composition

For several courses with assignments, combine a clear next action, a working
assignment view and substantive course material. Choose their arrangement for
the available page width. A single reading seminar can use the notebook pattern
in design.md instead. Keep design-research attribution and process commentary
out of the created workspace unless requested; preserve citations and source
qualifications for actual learning material.

## First screen

Prefer a full-width page with a quiet subject palette when MCP exposes that
setting. Do not assume full width was applied to a standalone home merely
because database records support it. If home width is unavailable or unverified,
use a continuous single-column study desk: one short priority with its deadline,
compact course navigation, then the inline Upcoming assignment table across the
available page width. Place reminders, course cards and substantive study material
after the working table. Keep the guide and weekly reset collapsed below the work.
Do not place the assignment table inside a narrow column or let stacked course
cards push the next deadlines below the first screen.

Use a roughly 22–28% side rail only after rendered inspection confirms that
reminders remain readable and the courses and next deadlines fit. A wide layout
may place courses before assignments if they fit in a single compact row. If
they stack or text wraps excessively, apply the single-column arrangement through
MCP rather than forcing the reference proportions. Course navigation is a compact
wayfinding aid, not a substitute for the useful course records and their material.

Give each course a meaningful colored icon carried through its assignment and
note references. Small gallery cards with wrapped content can fit three courses
without sacrificing titles. Show the next assignment and useful course context
such as office hours; do not show every property. Derive next-assignment summaries
from related work when supported. If using a static summary, label it as a
snapshot and do not imply it will update with assignment status.

The assignment table shows the fields needed to choose work: title, due, status;
add course if it fits without hiding the due date or status. Course remains
available on the record. Provide calendar and completed views and preserve
undated work. Use actual dates from sources, never decorative progress figures.

## Connected learning material

Courses and assignments use native relations. A course opens into its brief,
useful notes/material, and related work. Assignment pages contain the actual
brief, deliverable, criteria and a sensible next step; notes contain explanations,
not empty headings. Preserve supplied equations and source references. Do not
answer graded work on behalf of the learner when the request is only organization.

## Acceptance walk

See this week's priority, course choices and actual upcoming assignment dates on
the initial screen. At limited width, inspect the continuous layout rather than
requiring a side rail or one-row gallery. Open a course and assignment, return home, and switch to Calendar and
Completed. Check the completed item disappears from Upcoming without being lost.
Check unknown dates remain discoverable. Compare card density and side-column
balance with the reference; a course-link list beside generic callouts fails.

## Render and inspect the saved result

Build records and views first, then compose their existing blocks into the home.
Read the connection's current Markdown and view/layout documentation. For native
toggles and tabs, separate their label from child blocks with a blank line.
Preserve exact child-page/database tags during edits. A tool's success response
does not establish that moved blocks retained the intended order: inspect the
saved page and correct misplaced sections while preserving existing objects.
If moving existing database blocks into a new tab/column container changes sibling
order, fetch the saved hierarchy, then reapply the intended complete composition
using those same object IDs. Verify the second readback before deciding the native
layout is unavailable; do not discard working tabs merely because their first
move reordered the page.

Set width, card size, wrapped content and property visibility deliberately.
Check data-source update capabilities for database-record layouts, not just page
update capabilities. On connections exposing `page_layout`, read
`notion://docs/database-page-layouts`: pinned properties, sidebar details and
record full width can be configured there before UI inspection. Create and edit
all workspace content and settings through Notion MCP. Use the UI only to inspect
rendering and navigate; never repair the output through UI controls. If MCP lacks
a setting, report the exact missing capability and its visible effect. Adapt to
the available width without dropping essential work. Do not claim visual parity
when the reference requires an unavailable setting. Standalone page width and
database-record width are separate capabilities. Gallery card size, compact card
layout and wrapped gallery properties are also separate; table WRAP CELLS does
not establish gallery wrapping support. Hide duplicate linked-database titles
only when the connection supports doing so.
A tab intended as a working table must contain an inline database/view, not merely
a link to its full-page source. In Notion Markdown, verify `inline="true"` for
embedded work surfaces; reserve `inline="false"` for navigation destinations.
Use semantic colored page icons so mentions are recognizable, not a repeated
colored dot. Keep original assets and long detail accessible without dominating
the working first screen.

Verify home → record → related work → home, actual view filters and counts, and
at least one alternate view. Restore the intended everyday default view after
testing alternates so delivery opens on useful work. Inspect the rendered result at normal zoom with the
sidebar visible. Compare hierarchy, density and navigation against the selected
reference. Check useful work is visible above the fold, long titles wrap, and
essential columns do not overflow. Correct failures before delivery. If rendering
or a capability is unavailable, report that exact gap without claiming parity.

During skill evaluation, preserve the first result and the run's evidence. If
review finds a miss, change the reusable instructions and rerun or resume the
skill with only that revised guidance. Reviewer hand-polishing is not a passing
skill test. Equivalent layout and workflow matter more than identical wording,
page IDs, image pixels, or arbitrary record counts.
